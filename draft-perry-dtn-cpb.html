Probabilistic Contact Metadata for DTN Bundle Routing

Abstract

This document defines the Contact Probability Block (CPB), an extension block for Bundle Protocol version 7 (BPv7) that carries probabilistic routing metadata, such as contact or delivery probability estimates, with a bundle. Each CPB names the node that produced its estimates and labels them with a metric type and a profile, so that a receiver can tell what the values mean. The CPB carries routing metadata; it does not define routing. Routing protocols such as PRoPHET, CGR, MaxProp, RAPID, and Spray and Wait can produce or consume it, and none is required to.¶

The block uses deterministic CBOR encoding with compact binary16 probabilities, leaves endpoint identifiers unchanged, and uses BPSec Block Integrity Blocks when producers must be authenticated.¶

1. Introduction

Delay-tolerant networks (DTNs) often face uncertain contact schedules, for example during dust storms on Mars. Schedule-based routing such as Contact Graph Routing (CGR) [CGR] can delay delivery when a planned contact does not occur. [RFC9171] leaves route computation out of scope, so the Bundle Protocol does not itself define how such estimates are used. Probabilistic metadata about contacts and delivery can help routing protocols adapt their forwarding decisions.¶

This specification defines a bundle extension block, the Contact Probability Block (CPB), that carries such metadata between nodes. The CPB carries routing metadata; it does not define routing. How a routing protocol uses a CPB is up to that protocol. This document does not report experimental results or claim any routing-performance improvement.¶

CPB is an experimental extension block. It does not modify the bundle processing defined in [RFC9171], the security processing defined in [RFC9172], or the default security contexts defined in [RFC9173]. Nodes that do not implement CPB process bundles carrying it exactly as those specifications require for an unrecognized extension block.¶

1.1. Problem Statement

The Interplanetary Chapter of the Internet Society (IPNSIG) report on Solar System Internet architecture and governance [IPNSIG2023] discusses, among other topics, how bundles can be routed and forwarded when propagation delays are long, connectivity is intermittent, and topology information cannot be distributed promptly. One family of approaches ranks candidate next hops using estimates that are available locally or that travel with the traffic.¶

The CPB gives such estimates a common in-bundle encoding with an explicit metric type, producer, creation time, and validity, so that a node can tell what an estimate means and who made it. Section 5 positions CPB relative to existing DTN routing protocols, including PRoPHET [RFC6693], MaxProp [MaxProp], RAPID [RAPID], Spray and Wait [Spyropoulos05], Schedule-Aware Bundle Routing (SABR) [SABR], CGR [CGR], and CGR with uncertain contact plans [Raverta21]. CPB is a cross-protocol metadata container, not a replacement for any of these algorithms; each can produce or consume CPB data.¶

1.2. Motivation

DTN routing protocols work from contact schedules or from encounter history. In highly disrupted networks:¶

  • Contact schedules change unpredictably (dust storms on Mars, solar weather, orbital variations).¶
  • Historical data becomes stale.¶
  • Path computation elements (PCEs) can estimate probabilities but need a way to communicate them to forwarding nodes.¶

Carrying such estimates in bundles as a standard extension block gives DTN routing protocols an optional, common transport for them. Whether any protocol benefits is the subject of the planned experiment (Section 11).¶

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

In this document, requirements apply to the encoding of the CPB, its validation, the conditions under which a CPB is eligible for use, and the labelling of its contents. Text that describes how a routing protocol might use CPB values is informative.¶

1.4. Terminology

Contact Probability
The probability that a particular contact between two nodes occurs and can carry a bundle.¶
Delivery Probability
The probability that a bundle reaches its destination, possibly over several hops.¶
Estimate

Producer
The node that computed the estimates in a CPB, identified by its node ID in field 3.¶
Path Probability
An estimate specific to one next-hop node.¶
Default Probability
An estimate that is not specific to a next-hop node.¶
Metric Type
An identifier of the kind of estimate carried (for example, PRoPHET delivery predictability or CGR contact confidence).¶
Profile
The rules that fix what an estimate applies to and how it can be compared with other estimates. This document defines a default profile (Section 3.5.1).¶
Validity Duration
The time in milliseconds after creation during which an estimate is usable.¶

2. Architectural Considerations

2.1. Why Not URI Query Parameters

An earlier design considered carrying a probability in the destination EID, written as the string "ipn:100.1?prob=0.75". That design is not available and would be unsound:¶

  • The ipn URI syntax in [RFC9758] Section 4.1 has no query component, so the string is not a valid ipn URI.¶
  • [RFC9758] Section 7.5 states that elements of an ipn URI must not be regarded as carrying information about location, reachability, or other routing concerns.¶
  • The destination EID is in the primary block. Changing it at each hop would invalidate any BIB whose integrity scope includes the primary block ([RFC9173] Section 3.3.3), and would mix addressing with metadata that changes as the bundle moves.¶

2.2. Solution: Bundle Extension Blocks

This specification carries the metadata in an extension block, separate from endpoint identifiers. The destination EID is never changed. A node with a fresher estimate appends a new CPB rather than editing an existing one (Section 4.2), and integrity protection uses Block Integrity Blocks (BIBs) as described in Section 7.3.¶

3. Contact Probability Block

3.1. Overview

The Contact Probability Block (CPB) is a BPv7 bundle extension block that carries estimates computed by a producer: a source node, a path computation element (PCE), or a forwarding node. Each CPB names its producer, its metric type, and its profile, so that a receiving node can tell what the estimates mean and who made them.¶

3.2. Block Structure

The CPB is a canonical bundle block as defined in [RFC9171] Section 4.3.2. Its block-type-specific data (BTSD) is a CBOR byte string whose content is one CBOR-encoded cpb-data map.¶

The following annotated hex shows a complete CPB produced by node ipn:200.0. It carries a default probability of 0.75, a path probability of 1.0 for next-hop node ipn:100.0, a creation time, and a validity of one hour. The block flags are 0 and CRC type 0 omits the CRC. The surrounding bundle and any BIB are not shown.¶

The embedded-cbor rule of [RFC9171] Appendix B also allows a plain byte string. That alternative covers a BTSD replaced by ciphertext under a Block Confidentiality Block (BCB), as discussed in Section 7.3.3. A node can process a CPB's contents only when the BTSD holds a cpb-data map.¶

Field Semantics:¶

Field 0: Default Probability
An estimate that is not specific to a next hop. Its meaning depends on the metric type and profile (Section 3.5).¶
Field 1: Path Probabilities

An array of [next-hop, probability] entries. Each next hop is the node ID ([RFC9171] Section 4.2.5.2) of a node, encoded as an RFC 9171 eid array. Senders SHOULD NOT include more than 8 entries; see Section 3.4 for receiver limits.¶

For an ipn next hop, the producer SHOULD use the EID of the node's administrative endpoint, service number 0 ([RFC9758] Section 5.7), and encode the scheme-specific part as described in [RFC9758] Section 6.1. For a dtn next hop, the producer SHOULD use the form with an empty demux, which identifies a node ([RFC9171] Section 4.2.5.1.1). A next hop MUST NOT be the null endpoint (dtn:none) or an ipn LocalNode EID, which [RFC9758] Section 5.4 forbids in a transmitted bundle. The restriction on Private Use ipn EIDs in bundles leaving an administrative domain ([RFC9758] Section 5.5) applies to next hops and to field 3.¶

Field 2: Creation Time
The DTN time ([RFC9171] Section 4.2.6, milliseconds since 2000-01-01T00:00:00Z) at which the producer computed the estimates. As for bundle creation time ([RFC9171] Section 4.2.7), a producer without an accurate clock sets the value to 0. A CPB with field 2 absent or 0 is undated.¶
Field 3: Producer
The node ID of the producer, encoded as an RFC 9171 eid array under the same rules as a next hop. This field is mandatory. It is a claim; how it is authenticated is described in Section 7.2.1.¶
Field 4: Validity Duration
The number of milliseconds after the creation time during which the estimates are usable. A sender including field 4 MUST include a nonzero field 2, and a receiver MUST treat field 4 without a nonzero field 2 as malformed. When the creation time plus the validity duration is earlier than the receiver's current time, the CPB is expired.¶
Field 5: Metric Type
The kind of estimate carried, from the "CPB Metric Types" registry (Section 8). When absent, the metric type is generic (4).¶
Field 6: Confidence
A value in [0.0, 1.0] whose meaning is defined by the profile. The default profile defines no meaning for it; producers using the default profile SHOULD omit it.¶
Field 7: Version
The CPB format version. Absent or 1 means the format defined here. A receiver that does not support the version MUST NOT apply this document's field semantics to the CPB and MUST treat it as unusable (Section 3.2.2). A future change to the meaning or type of an existing field requires a new version. New optional fields that receivers can safely ignore use new keys without a version change.¶
Field 8: Profile
The profile under which the estimates were computed. Absent or 0 means the default profile (Section 3.5.1). Other values identify profiles agreed within the producer's administrative domain or domains; their meaning is outside the scope of this document. A receiver that does not know the profile for this producer MUST treat the CPB as unusable.¶
Keys above 8
Receivers MUST ignore map keys they do not recognize. A node MUST NOT remove or alter unrecognized keys in a CPB it forwards.¶

A producer MUST use only metric types registered in the "CPB Metric Types" registry or taken from its Private Use or Experimental Use ranges. A receiver that does not recognize the metric type MUST treat the CPB as unusable and MUST NOT reinterpret it as generic.¶

3.2.1. Block Processing Flags

The block processing control flags ([RFC9171] Section 4.2.4) of a CPB are set as follows:¶

  • Bit 4 (0x10), discard block if it can't be processed: A node that cannot process a block with this bit set removes the block ([RFC9171] Section 5.6, Step 4). Removing a block that a BIB targets can make the bundle unverifiable ([RFC9171] Section 4.4), and [RFC9172] Section 3.7 cautions against such flags on BIB targets. The producer therefore MUST NOT set bit 4 on a CPB that is, or is expected to become, the target of a BIB. Otherwise the producer MAY set it. With bit 4 clear, a node that does not implement CPB keeps the block and forwards it unchanged.¶
  • Bit 0 (0x01), replicate in every fragment: The producer MAY set this bit. A replicated CPB that is authenticated is still unusable in a fragment until reassembly, as described below.¶
  • Bits 1 and 2 (status report and delete bundle if the block can't be processed): These bits MUST be 0. A CPB must never cause a bundle to be deleted or a status report to be sent.¶
  • Bits 3, 5, and 6: These are reserved in [RFC9171] and MUST be 0. Bit 7 and higher: Senders MUST set unassigned bits to 0.¶

When a CPB is protected by BIB-HMAC-SHA2 with the integrity scope required in Section 7.3, its block flags are covered by the security result ([RFC9173] Section 3.3.3), so they cannot change after the BIB is created.¶

Fragmentation: A fragmenting node MUST NOT modify a CPB, including removing path entries or re-encoding its BTSD. The producer named in field 3 is the only node that can change what the CPB asserts.¶

Replicating a CPB does not by itself replicate a protecting BIB. When creating a BIB whose sole target is a CPB, the security source SHOULD set the BIB's "replicate in every fragment" flag before computing its security result. Fragmentation MUST NOT change authenticated BIB header fields after the security result is computed.¶

The authenticated profile in Section 7.3 binds a CPB to its containing bundle. Because fragmentation changes the primary block, primary-bound verification is not possible before reassembly ([RFC9173] Section 6.5). A node requiring authenticated CPB input MUST treat CPBs in fragments as unusable until reassembly permits verification. A node MUST NOT add a BIB or BCB to a bundle that is a fragment ([RFC9172] Section 5.2); the update models in Section 7.3 do not override this.¶

3.2.2. Malformed and Unusable CPBs

A CPB is unusable when it is malformed, has an unsupported version, metric type, or profile, is expired or outside the receiver's time limits (Section 4.1), or fails the receiver's authentication and authorization policy (Section 7). A node MUST treat an unusable CPB as absent for routing. CPB processing MUST NOT cause bundle deletion or a status report.¶

A node SHOULD forward an unusable CPB unchanged, since another node may be able to use it. A node MUST NOT remove a CPB that is the target of a security operation unless that node is the security acceptor for every operation targeting it and removes those operations as [RFC9172] Section 5.1.2 requires. A node MAY remove an unusable CPB that no security operation targets ([RFC9171] Section 4.4).¶

Core BP reception checks, including malformed canonical blocks and CRC failures ([RFC9171] Section 5.6), and BPSec policy processing still apply.¶

3.2.3. Cyclic Redundancy Check (CRC) Handling

CRC Type and CRC are defined in [RFC9171] Sections 4.2.1 and 4.2.2, and their placement in the canonical block in Section 4.3.2. The CRC is optional:¶

  • No CRC (recommended): Set CRC type to 0 and omit the CRC element, giving a five-element canonical block. Implementations MUST NOT emit a CBOR null CRC element when CRC type is 0.¶
  • Optional CRC: Implementations MAY use CRC type 1 (X.25 CRC-16) or type 2 (CRC32C).¶

A CRC detects transmission errors and does not authenticate a producer. When a CPB is protected by BIB-HMAC-SHA2, the CRC handling in [RFC9173] Sections 3.8.1 and 3.8.2 applies.¶

3.2.4. Hop Count Block Co-Presence

Bundles carrying a CPB SHOULD also carry a Hop Count block (block type 10, [RFC9171] Section 4.4.3), which limits looping independently of any probability-based forwarding.¶

3.3. Block Type Code

3.3.1. Code Point Before IANA Assignment

This specification requests a block type code from the "Bundle Block Types" registry (Section 8). Until IANA assigns one:¶

  • Implementations MAY use a value in the range 192-255, which [RFC9171] Section 4.3.2 makes available for private and experimental use.¶
  • The examples in this document use 200 (0xC8).¶
  • After assignment, implementations SHOULD use the assigned code.¶

3.3.2. Backwards Compatibility

A node that does not recognize the CPB block type follows [RFC9171] Section 5.6, Step 4: since bit 2 is never set on a CPB, the node removes the block if bit 4 is set and otherwise keeps it and forwards the bundle with the CPB unchanged. In either case:¶

  • The bundle's primary block is unaffected by the CPB.¶
  • Routing protocols that do not consume CPBs work as before.¶
  • Bundles without a CPB use ordinary routing.¶

3.4. CBOR Encoding

[RFC9171] Section 4.1 requires the CBOR encoding of all fields in all blocks to follow the core deterministic encoding requirements of [RFC8949], except that indefinite-length items are not prohibited. A producer MUST encode the cpb-data map following the core deterministic encoding requirements of [RFC8949] Section 4.2.1, including for nested items. A node MUST NOT re-encode the BTSD of a CPB it forwards.¶

The CDDL prelude includes float16 as a set of values, but CDDL cannot require a particular serialization of a value ([RFC8610] Sections 2.2.3 and 3.3). The schema therefore uses the range 0.0..1.0, and the precision guidance is given here. Producers SHOULD use probability values that are exactly representable in IEEE 754 binary16. Under the preferred serialization required by deterministic encoding, such a value is encoded in 3 bytes. Decimal values such as 0.95 are not exactly representable; the reference encoder rounds to the nearest binary16 value.¶

A value that is not representable in binary16 is encoded in 5 bytes (binary32) or 9 bytes (binary64). Receivers MUST accept all three finite float widths. They MUST treat NaN, +/-Infinity, and finite values outside [0.0, 1.0] as malformed. Clamping an out-of-range value to the interval is NOT RECOMMENDED, because mapping a corrupted value above 1.0 to certainty can amplify sinkhole attraction (Section 7).¶

A CPB BTSD MUST contain exactly one cpb-data map, with no trailing items or bytes. Map keys MUST be unique unsigned integers; duplicate keys, including duplicate unrecognized keys, make the CPB malformed, and receivers MUST detect them before a generic decoder collapses map entries. Known fields MUST use the CBOR types in the CDDL: booleans and tagged bignums are not uints, and probability fields require untagged floats even for 0 and 1.¶

Resource limits: Each path entry with an ipn next hop in the default allocator takes at least 9 bytes. To limit the effect of oversized CPBs on constrained links, receivers SHOULD enforce local limits on the number of path entries (8 is RECOMMENDED on constrained links), on BTSD length, and on the nesting depth and size of values under unrecognized keys. A receiver MAY treat a CPB that exceeds a local limit as unusable. The CDDL does not bound these sizes.¶

3.4.1. Invalid Float Handling

  • NaN (0xF97E00): Malformed.¶
  • +/-Infinity (0xF97C00, 0xF9FC00): Malformed.¶
  • Negative values and values above 1.0: Malformed.¶
  • Very small positive values: Decoded values strictly between 0 and 2^-14 (the smallest normal binary16 value) SHOULD be treated as zero, whatever the received float width.¶

A malformed CPB is unusable and is handled as described in Section 3.2.2. Implementations SHOULD log the error, subject to the rate limits in Section 6.4.¶

3.4.2. CBOR Encoding: Major Type 7

A probability value representable in binary16 is encoded with CBOR major type 7 and additional information 25: one initial byte 0xF9 followed by the 2 bytes of the binary16 value.¶

3.5. Metric Types and Profiles

CPB values are numbers in [0.0, 1.0], but different routing protocols compute them in different ways. Field 5 (metric type) says what kind of estimate a CPB carries, and field 8 (profile) says what the estimate applies to and how it was scaled. Field 3 says who computed it. Together they let a receiver interpret a CPB without knowledge that is not in the bundle, provided the profile is the default profile or one the receiver knows.¶

This document defines metric types 0 through 4:¶

0 (prophet-dp)
A PRoPHET delivery predictability as defined in [RFC6693] Section 2.1.2: a statistic of past encounters, not a probability that a scheduled contact occurs.¶
1 (cgr-confidence)
A probability that a planned contact in a contact plan occurs and can carry a bundle, as used by CGR [CGR] and by CGR with uncertain contact plans [Raverta21]. Contact start and end times, light time, and volume stay in the contact plan.¶
2 (maxprop-delivery-likelihood)
A score derived from MaxProp path cost [MaxProp], mapped so that a lower cost gives a higher value. The cost itself cannot be recovered from the value.¶
3 (rapid-utility)
A utility from a RAPID-style optimizer [RAPID], scaled into [0.0, 1.0]. It is a score, not a calibrated probability.¶
4 (generic)
An estimate with no defined meaning beyond its range. It is advisory, for example for experimental social or hybrid scores such as those of BubbleRap [BubbleRap] and SimBet [SimBet], until a metric type is registered for them.¶

3.5.1. Default Profile

The default profile (profile 0) fixes the meaning of each field for each metric type defined in this document. A producer that emits a CPB with field 8 absent or 0 MUST compute its values as follows:¶

  • All values are the producer's own estimates at the creation time (field 2), or at emission if the CPB is undated.¶
  • Field 0 is an estimate for the bundle's destination EID.¶
  • A path entry for next hop N is an estimate for forwarding the bundle from the producer to N, toward the bundle's destination.¶
  • Higher values are better.¶
  • Field 6 has no meaning under the default profile.¶

Per metric type, under the default profile:¶

Metric type 0
Field 0 is the producer's delivery predictability P_(producer,D) for destination D, and a path entry for N is the producer's current record of N's predictability P_(N,D), as learned in the PRoPHET exchange ([RFC6693] Section 2.1.2). Values are aged at the producer (Equation 2 of [RFC6693]) before encoding.¶
Metric type 1
A path entry for N is the producer's probability that its first planned contact to N that has not yet ended, as of the creation time, occurs and can carry the bundle. Field 0 is the producer's probability that the bundle reaches D over the routes its contact plan currently gives.¶
Metric type 2
Each value is 1/(1+c), where c is the MaxProp cost ([MaxProp]) of the producer's lowest-cost path to D, through N for a path entry.¶
Metric type 3
A path entry for N is the producer's RAPID utility for replicating the bundle to N, divided by the largest such utility over the producer's candidate next hops at the creation time. Field 0 is undefined and SHOULD be omitted.¶
Metric type 4
No meaning is defined beyond the rules above.¶

Under the default profile, two values are on a common scale only when they have the same producer, metric type, and profile. Values from different producers of metric type 0, 1, or 2 are computed by the same rule and can be compared as estimates, but each reflects only what its producer knew. Values of metric type 3 are scaled to the producer's own candidate set and are ordinal only within one CPB.¶

A producer that computes values in some other way MUST NOT label them with profile 0. It uses another profile value agreed within its administrative domain, or registers a new metric type.¶

3.5.2. Values of Different Metric Types

Values of different metric types, or of the same metric type under different profiles, have no common scale. A PRoPHET predictability of 0.7 and a CGR confidence of 0.7 do not mean the same thing. This document defines no way to combine such values, and a receiver MUST NOT present or log the result of combining them as a value of any metric type. Whether and how a routing protocol uses several metric types together is a matter for that protocol and remains an open research question.¶

A bundle can carry several CPBs with different metric types, for example one from a path computation element with cgr-confidence and one from a forwarding node with prophet-dp. Each CPB is labelled independently.¶

New kinds of estimate SHOULD be registered as new metric types (Section 8) rather than carried under an existing one with a different meaning.¶

3.6. Multiple CPBs in One Bundle

A bundle can carry several CPBs, added by its source or by nodes along its path. A receiver MUST treat each unusable CPB (Section 3.2.2) as absent before considering the others.¶

Among usable CPBs with the same producer, metric type, and profile, the one with the latest creation time is the producer's most recent statement and supersedes the others. Block numbers identify blocks but do not indicate their order ([RFC9171] Section 4.1), so they cannot be used to decide which CPB is more recent. When two such CPBs are undated, or have the same creation time, and their contents differ, the receiver cannot tell which is current and MUST treat all of them as unusable.¶

CPBs from different producers are not ranked by this document. A routing protocol might prefer producers ranked higher by its trust policy (Section 7.2.2), then dated CPBs over undated ones, then later creation times. A CPB is a single statement by its producer: taking some fields or path entries from one CPB and others from another produces a combination that no producer stated, so a consumer MUST NOT attribute such a combination to any producer.¶

Next hops in field 1, and the producer in field 3, identify nodes. Two EIDs identify the same node as follows:¶

  • ipn: The decoded allocator identifier and node number are equal ([RFC9758] Section 6.4). The service number is ignored. The two-element and three-element encodings of the scheme-specific part ([RFC9758] Sections 6.1.1 and 6.1.2), and any form in the default allocator, are compared by their decoded values.¶

A CPB MUST NOT contain two path entries for the same node under these rules, even with equal values. A receiver MUST treat such a CPB as malformed. Comparison by these rules does not permit a node to re-encode a received CPB.¶

A node using a selected CPB looks up its candidate next hop among the path entries. A next hop of any URI scheme can appear in a CPB for a bundle whose destination uses another scheme. When no entry matches, the CPB supplies no path estimate for that next hop; field 0, if present, is still the producer's estimate for the destination, and local routing state applies otherwise. A missing estimate is not the same as an estimate of 0.5 or of 0.¶

4. Operational Semantics

4.1. Creation and Time Limits

A CPB can be created by:¶

  • the bundle's source, using historical or predicted contact data;¶
  • a path computation element (PCE), using network-wide routing state; or¶
  • a forwarding node, using its own contact or encounter statistics.¶

The producer names itself in field 3. Producers SHOULD include a creation time (field 2) and a validity duration (field 4) whenever they have an accurate clock. Both are in milliseconds, the unit of DTN time ([RFC9171] Section 4.2.6).¶

A receiver applies its own time limits, configured for the deployment, in addition to field 4. A dated CPB is unusable at the receiver when any of the following holds:¶

  • Its creation time is later than the receiver's current time plus the receiver's tolerance for clock offset.¶
  • Its creation time plus field 4, when field 4 is present, is earlier than the receiver's current time.¶
  • Its creation time plus the receiver's maximum accepted age is earlier than the receiver's current time.¶

The stricter of field 4 and the receiver's maximum age therefore applies. Field 4 cannot extend a CPB's life beyond the receiver's limit, and the receiver's limit cannot extend it beyond field 4. This document sets no default tolerance or maximum age; suitable values depend on light time, contact intervals, and clock quality (Section 6.7). For example, a deployment between Earth and Mars might accept ages of a day or more, while a terrestrial deployment might accept an hour.¶

An undated CPB cannot be checked against these limits. A receiver MUST treat an undated CPB as unusable unless its local policy explicitly accepts undated CPBs from that producer.¶

4.2. Processing at Forwarding Nodes

A node that implements CPB and forwards a bundle carrying CPBs typically:¶

  1. validates each CPB and sets aside unusable ones (Section 3.2.2);¶
  2. selects the CPBs relevant to its routing protocol (Section 3.6) and looks up its candidate next hops (Section 3.6.1);¶
  3. uses the values as one input to its routing decision, as its routing protocol defines; and¶
  4. forwards the bundle with every CPB it received, unchanged.¶

A node MUST NOT modify a CPB it did not produce. A node with a fresher estimate MAY add a new CPB naming itself as producer, subject to the fragmentation and security constraints in Section 3.2.1 and Section 7.3. Adding a CPB leaves the integrity protection of existing CPBs intact.¶

4.3. Usage in Routing Algorithms

This section is informative. Routing algorithms might use CPB values in several ways:¶

  • Local state first: Nodes that keep native routing state (a PRoPHET table, a CGR contact plan, MaxProp tables) might prefer it over values from other producers unless local policy imports CPBs as authoritative for a domain or metric type.¶
  • Thresholds: forward when an estimate exceeds a threshold.¶
  • Weighted selection: choose among next hops in proportion to their estimates.¶
  • Replica placement: when a local spray or epidemic policy already holds a copy budget, rank candidate relays by their estimates. A CPB does not carry a copy budget (Section 5.4).¶
  • Priority: favor bundles with higher estimates during congestion.¶

4.4. Stability Considerations

This section is informative. Forwarding on estimates creates feedback between routing decisions and observed behavior. Three effects are relevant:¶

Herding
When many sources see the same high estimate for one relay, they can all forward to it. The relay congests and its real delivery probability drops, while CPBs in flight still carry the old estimate. In a DTN, updated CPBs can take hours to arrive.¶
Route oscillation
If a node changes route whenever an estimate crosses a threshold, small changes near the threshold make traffic move back and forth between routes.¶
Synchronized congestion
In dense topologies, many nodes reacting to the same CPB at once can congest together, much as TCP flows synchronize in IP networks, but with longer recovery because of DTN delays.¶

Techniques that can reduce these effects include:¶

  • Hysteresis: separate thresholds for moving to a route and away from it, for example 0.75 and 0.60.¶
  • Rate limiting: at most one change of route preference per contact opportunity for each source and destination, rather than per bundle.¶
  • Randomized tie-breaking: random choice among routes whose estimates differ by less than a small margin.¶
  • Load-aware discount: lowering a received estimate according to local knowledge of congestion at the next hop.¶
  • Bounded influence: limiting how far one CPB can move a decision compared with the node's own observations.¶

This document gives no control-theoretic analysis of these effects; that is a research question for the experiment (Section 11).¶

5. Relationship to Existing DTN Routing Protocols

This section is informative. It positions CPB relative to existing families of DTN routing protocols, several of which are surveyed in [IPNSIG2023].¶

5.1. PRoPHET (RFC 6693)

PRoPHET [RFC6693] is an epidemic protocol with strict pruning. Each node maintains delivery predictabilities P_(A,B) updated on encounters (Eq. 1), aged over time (Eq. 2), and optionally improved by transitivity via an intermediate (Eq. 3). During a contact, peers exchange a Routing Information Base (RIB) of destination-scoped predictabilities, then apply a local forwarding strategy (for example GRTR / GTMX) and queueing policy. Positive delivery acknowledgments prune residual copies.¶

What CPB carries for PRoPHET: metric-type 0 values that a producer has already computed (aged, optionally transitive) for the bundle destination and/or candidate next hops. CPB is an optional in-bundle hint so downstream nodes that do not speak the full PRoPHET RIB exchange can still see a snapshot of the producer's P.¶

What stays local (not CPB): aging constants (gamma, K), P_encounter / beta parameters, the full RIB dictionary, Hello / anti-entropy session state, bundle offer and response TLVs, custody policy, and named forwarding/queueing strategies. CPB does not replace the PRoPHET control plane in RFC 6693 Sections 3-5.¶

5.2. MaxProp

MaxProp [MaxProp] estimates delivery likelihood from encounter history, prefers low path-cost relays, prioritizes new packets by hop count, uses hop-lists to avoid cycles, and floods delete-ACKs so peers can drop delivered bundles. Buffer drop order is tightly coupled to the same likelihood metric used for forwarding.¶

What CPB carries: metric-type 2 as a lossy [0.0, 1.0] higher-is-better score obtained by inverting MaxProp path cost into a delivery-likelihood proxy so foreign nodes can rank next hops without MaxProp's full peer exchange.¶

What stays local: cost vectors, hop-lists, delete-ACK flooding, and the dual use of likelihood for queue-drop priority. A CPB-aware node might still use metric-type 2 values as one input to local drop ranking.¶

5.3. RAPID

RAPID [RAPID] treats routing as a resource allocation problem: it computes a per-packet utility (often over expected delay under bandwidth and storage constraints) and replicates in decreasing marginal-utility order. Peers may exchange delay samples or related metadata to refine utilities.¶

What CPB carries: metric-type 3 only after the producer normalizes utility into [0.0, 1.0]. CPB does not carry raw delay distributions, residual bandwidth, or multi-objective utility vectors.¶

5.4. Spray-and-Wait Family

Spray-and-Wait [Spyropoulos05] limits replication to L copies. Binary spraying and Spray-and-Focus variants choose relays uniformly or by a utility in the focus phase. The remaining copy count is the primary control state.¶

What CPB carries: optional ranking hints (metric-type 0/1/2/3/4) for whom to spray to when a node chooses non-uniform targets.¶

What stays local / out of scope for CPB: the integer L remaining-copy counter and spray-phase state. Those are replication-control metadata, not probabilities; they need a different extension or local header if standardized later. CPB does not encode L.¶

5.5. Epidemic and Summary-Vector Protocols

Classic epidemic routing and many DTN anti-entropy designs exchange summary vectors of buffered bundle IDs so peers can request missing copies. That inventory exchange is orthogonal to probability metadata. CPB neither replaces summary vectors nor carries bundle-set digests. A node may still attach a CPB when forwarding a copy so receivers learn the forwarder's confidence snapshot.¶

5.6. Contact Graph Routing (CGR)

Contact Graph Routing [CGR] and schedule-aware routing as specified in SABR [SABR] compute earliest-arrival (or related) routes from a contact plan: contact intervals, data rates, one-way light times, and residual volume. CGR-UCoP [Raverta21] extends CGR using route delivery probabilities derived from Routing under Uncertain Contact Plans (RUCoP).¶

What CPB carries: metric-type 1 confidences, which under the default profile (Section 3.5.1) apply to the producer's next planned contact to each next hop. This lets the producer's view of contact reliability travel with traffic when contact-plan distribution is slow or partial.¶

What stays in the contact plan: time windows, rates, OWLT, and residual capacity. CPB is not a substitute contact plan. The closest architectural precedent for in-band routing metadata is the CGR Extension Block [CGREB]. This document does not compare forwarding policies or report routing-performance results; CGR-UCoP is prior art for simulation, not the definition of the block.¶

5.7. Social and Hybrid Metrics

Protocols such as BubbleRap [BubbleRap], SimBet [SimBet], and related social DTN routers use centrality, community labels, or similarity rather than pure encounter probability. Those scores may be published as metric-type 4 (generic) with local documentation, or as new metric-type codepoints via the IANA registry in Section 8. They have no common scale with prophet-dp or cgr-confidence values (Section 3.5.2).¶

5.8. DTNMA (RFC 9675)

[RFC9675] defines a DTN management architecture orthogonal to routing. A DTNMA agent could monitor CPB-related metrics (frequency of stale CPBs, scheme mismatches, BIB verification failures) for network health assessment.¶

5.9. Neighborhood Advertisement and Scheduled Topology

Secure Advertisement and Neighborhood Discovery (SAND) [I-D.ietf-dtn-bp-sand] is a DTN Working Group control-plane protocol. Nodes advertise local topology and link metrics such as data rate and one-way delay to topological neighbors. Those advertisements are not carried as metadata on application bundles.¶

CPB is complementary, not a substitute for SAND. Contact intervals, rates, OWLT, and residual volume remain in the contact plan or in SAND/SABR inputs. CPB carries optional in-bundle quality or confidence samples (metric-type tagged) along the data path when those estimates should travel with the bundle. A node might use SAND metrics and CPB values together, but a SAND rate or delay advertisement is not a CPB value of any metric type, and a CPB value is not a SAND metric.¶

Long-lived contact schedules and bandwidth as managed objects are modeled in Time-Variant Routing work, including the scheduled-attributes YANG model [I-D.ietf-tvr-schedule-yang] and related contact-plan YANG. Inter-domain reachability with optional time windows is the subject of the DTN Peering Protocol [I-D.taylor-dtn-dpp]. None of those documents define the CPB extension block.¶

5.10. Relationship to Updates of BPv7

[RFC9171] (BPv7) has been updated by [RFC9713] (administrative record types registry, January 2025) and [RFC9758] (ipn URI scheme updates, May 2025). Neither update affects the wire format defined in Section 3:¶

  • [RFC9713] concerns administrative record types; CPB is an extension block, not an administrative record, so RFC 9713 does not apply directly.¶
  • [RFC9758] updates the "ipn" URI scheme. CPB carries ipn EIDs in the RFC 9171 eid encoding as updated by RFC 9758, with the restrictions in Section 3.2.¶
  • RFC 9171 erratum 8376 [Errata8376] records concerns about extension-block placement during fragmentation. It is Held for Document Update and does not replace the published fragmentation rules. CPB's handling under those rules is defined in Section 3.2.1.¶

Related security work includes the BPSec COSE context [I-D.ietf-dtn-bpsec-cose] (work in progress) and ACME DTN Node ID validation [RFC9891]. These address security contexts and credential provisioning, respectively. Neither independently establishes a credential's authority over a CPB producer identifier.¶

5.11. Summary: CPB as Cross-Cutting Metadata

Across the families above, a recurring split appears:¶

  • In-bundle scalar quality (CPB): a [0.0, 1.0] estimate labelled with its producer, metric type, and profile, with an optional per-next-hop list, creation time, and validity.¶
  • Control-plane state (not CPB): encounter RIBs, contact plans, summary vectors, copy counts, hop-lists, delete-ACKs, Hello sessions, and strategy/queue policy parameters.¶

The Contact Probability Block is designed as that cross-protocol scalar layer rather than a replacement for any algorithm. Algorithms can consume CPBs for forwarding rank, replica placement, or buffer-drop priority, and can produce CPBs for downstream nodes, without requiring the peer to implement the producer's full protocol.¶

6. Operational Considerations

This section collects deployment, sizing, and operational guidance. It draws on Section 4, Section 9, and Section 3.3.2.¶

6.1. When and Where to Produce CPBs

A CPB can be produced by a bundle's source, a PCE, or a forwarding node (Section 4.1). Deployments SHOULD document which producers are authoritative for which traffic and which profiles they use.¶

With long propagation delays, as between planets, a PCE close to the source is often best placed to produce a current estimate. In low-delay terrestrial meshes, the first forwarding node may have fresher observations.¶

6.2. Bundle Store and Memory Sizing

Without the strip-and-replace model (Section 7.3.2), bundles can accumulate CPBs across hops. The examples in Section 9 range from 19 to 128 bytes per canonical block before any BIB; they are illustrations, not bounds. Bundle stores on memory-constrained nodes need to allow for this overhead, and nodes apply the limits in Section 7.4.¶

6.3. Processing on Constrained Nodes

Decoding and storage costs depend on the fields present, identifier lengths, implementation, and hardware. Verifying a BIB for each use adds to this; caching is discussed in Section 9.1. Route recomputation triggered by new estimates can be bounded by the techniques in Section 4.4.¶

6.4. Logging, Monitoring, and OAM

Nodes SHOULD log CPB events such as malformed CPBs, unsupported versions, metric types, or profiles, CPBs that are expired or dated in the future, and BIB verification failures, using deployment-defined management procedures. Such events help diagnose clock offsets and misbehaving producers. The adaptive information push in [RFC9675] Section 4.3 is architectural guidance; neither it nor this document defines a CPB event schema. Logging SHOULD be rate limited so that malformed input cannot exhaust management resources.¶

6.5. Partial Deployment

CPB can be deployed incrementally. A node that does not implement CPB keeps a CPB whose bit 4 is clear and forwards it unchanged (Section 3.3.2). Producers therefore SHOULD leave bit 4 clear when the CPB is meant to cross nodes that do not implement it. Operators may monitor the share of nodes that use CPBs and produce them only where enough consumers exist.¶

6.6. Congestion and Storage Pressure

Forwarding on estimates tends to concentrate traffic on routes with high estimates, which under load can congest those routes and fill stores at intermediate nodes. The techniques in Section 4.4 help. Operators can watch queue depths and delivery ratios on such routes and fall back to routing without CPBs, or reduce CPB production, during overload.¶

6.7. Clock Considerations

Field 2 is a DTN time in milliseconds, and field 4 is a duration in milliseconds from that time. With light-time delay or unsynchronized clocks, the receiver's clock-offset tolerance and maximum age (Section 4.1) need values chosen for the deployment; one deployment may need much larger values than another. A producer without an accurate clock emits undated CPBs, which receivers accept only by explicit policy.¶

7. Security Considerations

7.1. Threat Model

  • False estimates: An attacker injects inflated values to attract traffic and then drop it (a sinkhole), or deflated values to avoid carrying traffic.¶
  • Forged attribution: An attacker produces a CPB that names another node in field 3.¶
  • Stale data and replay: A captured CPB, or a whole bundle, is replayed after conditions have changed.¶
  • Stripping and downgrade: An on-path node removes a fresher or authenticated CPB, or its BIB, so that receivers fall back to an older or unauthenticated estimate.¶
  • Resource exhaustion: A node appends many CPBs, or large values under unrecognized keys, to consume bandwidth, storage, or processing at downstream nodes.¶
  • Biased semi-trusted relays: A relay holding valid credentials produces estimates that favor itself or disfavor competitors or destinations.¶
  • Inter-domain trust: A CPB from a producer trusted in one administrative domain enters a domain that has no basis for trusting it.¶
  • Inference: Observers learn topology, schedules, or traffic patterns from CPB contents (Section 7.5).¶

7.2. Trust Model

DTN deployments range from a single operator's interplanetary relay network to terrestrial meshes run by many parties, so this document does not mandate one trust model. Each deployment decides which producers it accepts CPBs from, which security contexts and credentials authenticate them, and what happens to CPBs that fail those checks.¶

7.2.1. Producer Authentication and Authorization

Any node on a bundle's path can add a CPB. Field 3 is a claim by whoever created the block. A receiver MUST NOT treat field 3 alone as establishing who produced a CPB or as conferring that producer's trust.¶

A receiver that requires authenticated CPBs MUST, before treating a CPB as usable:¶

  1. verify a BIB protecting the CPB as required in Section 7.3;¶
  2. check that the BIB's security source and field 3 identify the same node under the rules in Section 3.6.1;¶
  3. check that the key or credential that verified the BIB is held only by that node, or by nodes that local policy treats as equivalent to it for this purpose; and¶
  4. check that local policy authorizes that producer for the metric type and profile of the CPB.¶

Step 3 matters because BIB-HMAC-SHA2 uses symmetric keys ([RFC9173] Sections 3.1 and 3.5). When several nodes share a key, any of them can produce a valid BIB naming any of the others as security source, and [RFC9172] Section 8.1 notes that shared keys make every holder equivalent to the most privileged one. A shared key therefore authenticates only membership in the group that holds it. Deployments that need attribution to an individual producer MUST use per-producer or pairwise keys, or a security context with digital signatures such as the COSE context [I-D.ietf-dtn-bpsec-cose]. With a group key, a receiver MUST NOT rank CPBs by the individual producer named in field 3.¶

A CPB that fails these checks is unusable at that receiver. Its retention follows Section 3.2.2 and local BPSec policy.¶

7.2.2. Conflicting CPBs

When a bundle carries CPBs from different producers with different values, a receiver that requires authentication considers only CPBs that pass Section 7.2.1. Which producer to believe is then a matter of local trust policy and routing protocol (Section 3.6).¶

7.2.3. Downstream Handling of Upstream BIBs

A node that cannot verify an upstream BIB (for example, because it lacks the key, the credential has expired, or it does not support the security context) follows local BPSec policy. For routing:¶

  • Strict (recommended default): treat the CPB as unusable, and forward it with its BIB, where BPSec policy permits, so that downstream nodes with the right credentials can still use it. A node that requires authenticated CPBs MUST behave this way.¶
  • Permissive: use the unverified CPB as advisory input, where local policy accepts unauthenticated CPBs. This is unwise in adversarial environments but can be reasonable in a cooperative single-operator network while credentials are being rolled out. The receiver still applies the CPB's metric type and profile and MUST NOT grant it the trust of the producer it names.¶

A node MUST NOT remove an unverifiable protected CPB and protect it again with its own credentials, which would conceal that the upstream producer was never authenticated. A node that has a different estimate adds its own CPB instead, subject to Section 3.2.1.¶

7.2.4. Route Poisoning by Semi-Trusted Relays

A relay trusted enough to take part in the network, but not trusted to steer routing for the whole domain, can still degrade routing with biased estimates. Defenses at the CPB layer are imperfect. Possible mitigations include:¶

  • Plausibility checks: comparing a received value with local estimates of the same metric type and profile, using tolerances that the deployment defines, and discounting values that disagree.¶
  • Reputation: keeping per-producer scores based on past accuracy. CPB does not define a reputation mechanism; such state could be managed within the DTN Management Architecture ([RFC9675]), which does not define one either.¶
  • Bounded influence: limiting how far one CPB can move a decision (Section 4.4).¶

These raise the cost of poisoning and make casual misbehavior easier to detect. They do not defeat a capable adversary. Stronger frameworks, such as reputation aggregation or attestation chains, are out of scope.¶

7.2.5. Inter-Domain Trust

When a bundle carrying a CPB crosses into another administrative domain, the receiving domain has no prior basis for trusting the producer. Approaches include:¶

  • an agreement naming the foreign producers and credentials that are accepted;¶
  • a gateway at the boundary that uses foreign CPBs as advisory input and adds its own CPB with its own assessment; or¶
  • treating all foreign CPBs as unusable and producing new CPBs inside the domain.¶

A gateway can remove a foreign CPB only as Section 3.2.2 allows. Deployments SHOULD document their inter-domain CPB policy. This document does not standardize inter-domain trust.¶

7.2.6. Replay

Fields 2 and 4, with the receiver's limits in Section 4.1, bound how old a usable estimate can be. They do not prevent reuse within the accepted window. The integrity scope required in Section 7.3 binds a CPB to its bundle, including the destination, so an unchanged CPB and BIB cannot be moved to a bundle with another destination. Listing the CPB as a BIB target without that scope would not prevent such a move. Binding does not prevent replay of a whole valid bundle; deployments that need to suppress such replays can combine their freshness policy with duplicate-bundle detection based on the source node ID and creation timestamp ([RFC9171] Section 4.2.7).¶

7.3. Integrity Protection

Where CPBs cross untrusted networks or producer authentication is required, CPBs MUST be protected with Block Integrity Blocks (BIBs) [RFC9172] using a security context that authenticates the security source with a MAC or a digital signature. A bundle without a CPB needs no security operation because of this document.¶

For authenticated use, the CPB MUST be a security target of the protecting BIB, and that BIB MUST authenticate the complete CPB block-type-specific data, the CPB's block number and block processing control flags, and the containing bundle's primary block, which includes the destination. With BIB-HMAC-SHA2 ([RFC9173] Section 3), senders MUST use integrity scope flags value 7 (Section 3.3.3), explicitly or as that context's default, which covers the primary block, the target's block header, and the security header. Receivers MUST check the scope before accepting the CPB for authenticated use, even when the MAC verifies. Other contexts MUST give equivalent coverage.¶

A BIB protecting a CPB SHOULD have only CPBs from the same producer as its targets, so that accepting and removing that BIB's operations never affects other blocks.¶

7.3.1. Append-Only Model

On a bundle that is not a fragment, a producer adds a CPB and a BIB that targets it. Later nodes with fresher estimates MAY add their own CPBs and BIBs. They MUST NOT modify a protected CPB or invalidate its security operation. A node acting only as a security verifier keeps the verified operation, as [RFC9172] Section 5.1.2 requires.¶

7.3.2. Strip-and-Replace Model

On a bundle that is not a fragment, a node configured as the security acceptor for the BIB operation protecting a CPB MAY instead accept that operation, remove it as [RFC9172] Section 5.1.2 requires, remove the CPB, and add a new CPB naming itself as producer, protected by its own BIB. A BIB left with no operations MUST be removed, and operations on other targets MUST be kept. The node MUST NOT remove a CPB that is the target of any operation it is not the acceptor for. Verifying a BIB does not make a node its acceptor. Deployments SHOULD use one model per administrative domain and document which nodes are acceptors.¶

7.3.3. Block Confidentiality

A CPB is meant to be read by forwarding nodes. Encrypting it with a Block Confidentiality Block (BCB) makes it unusable to every node that lacks the key. A producer therefore SHOULD NOT protect with a BCB a CPB intended for use at forwarding nodes along the path. A deployment MAY encrypt a CPB between a producer and a specific consumer, for example a gateway, where confidentiality of the estimates outweighs their use along the path. Such a BCB follows [RFC9172] Section 3.8. Integrity protection with a BIB remains appropriate in all cases.¶

7.4. Resource Exhaustion, Stripping, and Downgrade

Each node that adds a CPB increases the bundle's size. Receivers enforce the limits in Section 3.4 on each CPB. A node SHOULD also limit the number of CPBs it processes in one bundle and the total CPB bytes it accepts, and MAY treat CPBs beyond those limits as unusable. A node SHOULD NOT add a CPB to a bundle that already carries a usable CPB of its own with the same metric type and profile, unless the strip-and-replace model applies.¶

BIBs detect modification but not removal: an on-path node can remove an unprotected CPB, or, in violation of Section 3.2.2, a protected CPB together with its security operations. Receivers cannot detect that a fresher CPB was removed. Receivers that require authentication are not affected by the removal of a BIB alone, since an unprotected CPB is unusable to them. Absence of a CPB never forces a routing outcome; it only leaves the receiver with local routing state.¶

7.5. Privacy Considerations

CPB contents can reveal information about a network and its operators:¶

  • Field 3 names the producer, and path entries name nodes that the producer expects to reach, exposing parts of its neighbor set.¶
  • Values of metric type 1 reveal how reliable the producer believes particular planned contacts are, which can indicate schedules, positions, or link conditions.¶
  • Values of metric type 0 summarize encounter history, which for mobile nodes can indicate location and movement.¶
  • Changes in CPB values across bundles can indicate traffic patterns.¶

Deployments where this matters SHOULD limit the path entries a producer includes to those needed, produce CPBs only within trusted domains, and treat CPBs as unusable, or remove them as Section 3.2.2 allows, at domain boundaries. Bundles crossing an untrusted domain can also be carried inside an encapsulating bundle, which hides their extension blocks from that domain. Encrypting a CPB with a BCB protects its contents at the cost described in Section 7.3.3.¶

The specification needs to define the meaning of the value and which direction is better, what field 0 and path entries refer to under the default profile (Section 3.5.1), how the value is scaled into [0.0, 1.0], and when values from different producers can be compared.¶

Experts check that independent implementations could produce and interpret the metric consistently from the specification, and that the request does not reuse an existing value with a different meaning. A request that duplicates an existing metric explains why a separate value is needed. Registration does not endorse the accuracy of an estimator or any routing benefit.¶

9.1. Computational and Storage Overhead

Beyond wire bytes, CPB processing has costs that matter most on constrained nodes:¶

CBOR decoding
Cost depends on the number of entries, identifier lengths, the decoder, and floating-point support. This document gives no measured timings.¶
BIB verification
Authenticated use requires verifying a security operation. MAC and signature verification differ in cost, depending on the security context and hardware support, and on a constrained node without cryptographic hardware verification can dominate CPB processing. An implementation MAY cache a verification result while processing one bundle. A cached result MUST be invalidated if any covered bytes, the primary block, the credential, or the applicable authorization policy changes; block numbers alone do not identify a cache entry.¶
Route recomputation
New estimates can trigger route recomputation, whose cost depends on the routing algorithm and contact-plan size. The techniques in Section 4.4 can bound its rate.¶
Accumulated CPBs
Without the strip-and-replace model (Section 7.3.2), bundles can accumulate CPBs across hops, each with its encoded length, any BIB, and implementation bookkeeping. The limits in Section 7.4 apply.¶
Freshness checks
Cached estimates need the time checks of Section 4.1 before use. One comparison per CPB suffices, since fields 2 and 4 apply to the whole block.¶

On constrained nodes, processing and storage costs often matter more than wire bytes. Implementations are encouraged to publish measured overhead with interoperability reports.¶

11. Experiment Description

The experiment associated with this Experimental specification evaluates whether carrying estimates in an extension block is useful and safe for DTN forwarding. No results are reported in this document and no performance benefit is asserted.¶

What is evaluated
The same routing implementation with and without CPB consumption, under identical contact plans, traffic, resource limits, and random seeds, including scheduled and uncertain contacts, congestion, and partial CPB deployment. Estimate quality is varied in error, age, availability, and update frequency, including stale, missing, inconsistent, and deliberately misleading estimates. Interoperability is evaluated between independent BPv7 implementations for CPB encoding, unknown fields, multiple blocks, legacy nodes, authentication, added CPBs, and fragmentation.¶
Metrics
Delivery ratio, delivery delay, transmission volume, storage and processing use, route-change frequency, behavior when estimates are degraded, and the rate of correct decoding and handling of unusable CPBs across implementations.¶
Duration
The experiment runs for two years after publication of this document.¶
Success criteria
The experiment is successful if all of the following hold: (1) at least two independent implementations interoperate on the wire format and processing rules of Section 3; (2) nodes that do not implement CPB forward bundles carrying CPBs without error; (3) when estimates are stale, missing, or adversarial and authentication is applied as in Section 7, CPB consumption causes no statistically significant reduction in delivery ratio and no statistically significant increase in median delivery delay, at the 95% confidence level, compared with the same algorithm without CPB; and (4) in at least one class of scenarios with uncertain contacts, CPB consumption improves delivery ratio, median delivery delay, or transmission volume by at least 5%, significant at the 95% confidence level. Scenarios, baselines, sample sizes, and analysis methods are fixed before execution, and configurations, data, uncertainty, and unsuccessful outcomes are published with the results.¶
Failure outcome
If criterion (1), (2), or (3) is not met, the results are published with a recommendation that CPB not be deployed, and the author will ask that this document be reclassified as Historic. If only criterion (4) is not met, the results are published as a negative result and no further standardization of CPB is pursued.¶

Appendix A. Mars Mission Scenario

This appendix is informative. Consider a Mars rover (ipn:200.0) sending to Earth through an orbiter (ipn:100.0):¶

  1. Initial contact: During dusty conditions, the rover creates a status bundle with a CPB naming itself as producer, metric type 1 (cgr-confidence), the default profile, a path probability of 0.6 for next hop ipn:100.0, a creation time, and a validity of 3600000 ms (one hour). Under the default profile, 0.6 is the rover's probability that its next planned contact with the orbiter occurs and can carry the bundle.¶
  2. Routing at the rover: The rover's routing protocol might weigh this low confidence against waiting for a later contact with a higher confidence.¶
  3. Later bundles: When the dust clears, the rover produces later bundles with a CPB carrying 0.95 and a new creation time.¶
  4. Downstream: The orbiter and relays on Earth see that the CPB describes the rover's contact to the orbiter, not their own outgoing contacts, and rely on their own routing state for their decisions.¶

If the first bundle is delayed ten hours, the creation time plus field 4 is earlier than the receiver's current time, so the CPB is expired and unusable under Section 4.1. This document defines no decay of values after expiry.¶
